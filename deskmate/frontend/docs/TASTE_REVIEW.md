# DeskMate 第二次产品与视觉评审

日期：2026-11-06。对象：当前 `feat/deskmate-frontend` 工作区的第一版前端。依据：新安装的 design-taste-frontend（tasteskill 2.5.0）中 Copy、System 等设计规则，以及当前桌面/390px 手机截图和实际 Vue/CSS 源码。本次是设计复审，不增加运行测试结果。

## 一、评审结论

当前版本具备工程基础和一致的暖绿方向，但视觉表达仍带有生成式模板特征：英文眉题、情绪化大标题、大面积色块、均质圆角卡片、过小且过淡的辅助文字。最值得保留的是清楚的业务导航、真实接口边界、工作台配置、可追踪执行和隐私约束。

第二版应把「当前正在做什么、设备是否执行成功、下一步能做什么」放到视觉中心。建议方向是**安静、清楚的桌面控制台**，主色继续使用现有深绿，通过真实状态和执行反馈建立产品辨识度。

## 二、这个 skill 的适用边界

安装来源为 https://github.com/Leonxlnx/taste-skill，安装名 `design-taste-frontend`。技能文件位于 `/Users/howen/.codex/skills/design-taste-frontend/SKILL.md`。安装后下一轮对话自动可用；本轮已直接读取技能文件及相关参考规则。

它的当前版本主要服务公司官网和产品展示页。适用于桌伴的原则包括：朴素且具体的文案、真实产品内容、统一视觉系统、对齐、可读性、克制而明确的交互反馈。以下规则不直接作为控制台验收条件：

- 每个内容区恰好占一到两屏、第一屏只放 hero：会降低频繁操作的效率。
- 软件页加入 shader、场景或循环动画：不直接帮助专注与设备操作。
- 大量照片：控制台主要应呈现工作台、状态与执行结果；登录页插画可缩减，但不需要用无关照片替代。
- 禁止出现示例标记：本项目有纯界面预览，必须继续明确标识示例数据。
- 禁止视觉下方说明：图表的单位、口径、空调推测状态等仍需保留。

没有将官网的 consistency/layout 检查器作为本项目的通过证明；当前没有新的多尺寸自动浏览器检查结果。

## 三、按优先级处理的问题

### P0：字号和对比度影响实际阅读

CSS 存在大量 8–10px 标签、注释和按钮文案；手机样式还出现 6–9px 的信息。它们在缩略图里显得整洁，但不适合实际使用。建议正文 14–16px，标签与辅助文字原则上不低于 13px；缩减内容和调整布局来容纳文字。

下表按源代码指定的前景/背景色计算 WCAG 对比度，保留两位小数用于说明，不是逐元素的全站审计：

| 位置 | 前景 / 背景 | 对比度 | 处理 |
| --- | --- | --- | --- |
| 英文眉题 | #8c988b / #f7f8f4 | 2.82:1 | 优先删除装饰性英文，保留内容需加深 |
| 预览提示 | #7e8b70 / #eef2e7 | 3.18:1 | 提示关系到数据真实性，需要更清晰 |
| 设备补充说明 | #89967b / #ffffff | 3.13:1 | 加深，尤其空调「推测状态」 |
| 页面说明 | #7c8971 / #f7f8f4 | 3.47:1 | 加深并统一字号 |
| 深绿专注卡说明 | #9fb5a2 / #284f3d | 4.22:1 | 小字号文字仍需调整 |
| 主文字 | #293b31 / #ffffff | 11.90:1 | 可保留 |

普通文本的 WCAG AA 对比度要求是至少 4.5:1，大字有不同阈值。来源：[W3C Contrast Minimum](https://www.w3.org/WAI/WCAG22/Understanding/contrast-minimum.html)。

### P0：手机首屏的操作层级不足

390×844 截图中，从页头到专注卡、疲劳卡，占据了首屏的大部分空间，设备控制落在其后；底部导航只有图标。用户想调灯或空调时需要进一步寻找。

建议移动端优先顺序：当前工作台与连接状态 → 紧凑专注计时和主操作 → 台灯/空调快捷控制 → 关怀状态摘要 → 环境及节奏详情。健康服务不可用时收为一行状态，不保留大面积空卡。

保留清楚的文字导航，可采用四个常用入口加「更多」，或为当前导航补短标签；偏好设置与演示沙盒无需占用同等首屏权重。主操作和温度加减的可点击区域以 44×44px 作为设计目标；这属于本项目的易用性目标，不将 44px 错称为 WCAG AA 的统一门槛。

### P1：文案占用了任务和状态的位置

首页存在页面口号与专注卡口号两层表达。它们可以出现在许多专注产品中，难以说明桌伴当前做了什么。每个业务页都重复英文眉题、大标题、副标题，也增加了相似模板感。

| 当前文案 | 建议呈现 |
| --- | --- |
| 把时间，留给心流 | 我的工位 |
| 让世界安静一点，让灵感再近一点 | 当前工作台名称；下面显示本次目标 |
| 每一种投入，都有专属工位 | 工作台 |
| 你的想法，桌伴接住 | 桌伴助手 |
| 回头看，每一步都算数 | 每日复盘 |
| 你的节奏，你来定义 | 偏好设置 |
| 让工位刚刚好 | 设备控制 |

专注区域用「软件工程项目」「目标：完成需求分析」「专注中 · 剩余 32:18」建立层次，数字仅使用实际服务端状态。品牌语可以保留在登录页的一处。

开始/结束、设置保存和失败提示继续使用明确动词，避免把按钮写成情绪表达。演示页可以比日常控制台保留更多场景引导。

### P1：产品特色没有得到足够的执行反馈支撑

当前视觉上最醒目的是普通专注时钟和疲劳仪表。桌伴真正独特的内容是电脑与环境协同执行，以及失败后的清楚反馈。只靠 toast 和较低位置的通知列表，不容易看出一次复合指令到底完成了哪些步骤。

建议在专注区或助手结果中展示最近一次任务的确认结果。必须按现有接口能力区分：

- 台灯状态已经变化：可由 devices 增量确认。
- 专注已经开始/暂停：可由 FocusState 确认。
- 网页对话执行了哪些工具：可由 SSE tool 事件显示。
- 通过 focus/start 开始工作时，Windows 各启动项的完整结果：当前 REST 只返回 FocusState，需后端补充执行明细或对应事件。

没有工具结果时不能推断「VS Code 已打开」或「所有窗口已排列」。应先展示能证明的状态，再共同约定缺少的执行数据。

### P1：统一组件系统，减少卡片和装饰种类

目前自定义 button/light/secondary/icon-button 与 Element Plus 按钮同时承担业务操作，尺寸、圆角和反馈略有差别。统计、关怀、设备、通知大量使用相似白色圆角容器，降低信息层次。

建议明确一套主按钮、次按钮、文本按钮和危险操作样式；统一控件高度、焦点、禁用、加载与按压反馈。主绿保留为品牌/操作色，正文和辅助信息回到更清晰的中性色；环境提醒用有限的语义色，去掉没有状态意义的淡紫等装饰底色。设备控制保留实体卡片，统计和通知可用更轻的分组或列表。

图标目前基本保持同一线性风格，可以保留；以后出现 VS Code、Chrome 等真实产品时应使用其真实图标，而非画近似标志。桌伴自己的 SVG 标志属于原创品牌资产，无需更换成第三方图标。

### P2：精简首页，区分日常与演示

日常首页默认关注本次专注、环境和异常；设备在线数、重复隐私说明、空通知卡可以降低视觉权重。演示注入控件继续留在独立页面，不能为了答辩让日常工位充满调试内容。

健康服务尚未接入的状态仍需真实呈现，但应减少其版面占用。图表没有记录时保持简洁空态，不通过示例曲线填满真实账号页面。性能优化继续关注 ECharts 分块和首屏实际加载，不以增加动效作为质量证明。

## 四、第二版建议的验收顺序

1. 重写页面和卡片标题，保留具体任务、状态、目标和可执行操作。
2. 建立字号、文本颜色、间距、控件尺寸和按钮状态的统一规范。
3. 重排手机首屏，保证专注主操作与常用设备控制容易找到。
4. 用真实后端数据强化执行反馈，缺少的明细列入契约协作请求。
5. 在 1440、1024、768、390 宽度重新浏览检查；核对对比度、缩放、长目标/长工作台名、离线和服务未接入状态。

这五步完成后，再决定是否需要额外视觉资产与微动效。现有通信层和业务分工可以继续复用。
