# TravelAgent：能对话、能查询、能保存的旅游规划助手

GitHub：[IntZhx2/IntZhx2/smart_agent](https://github.com/IntZhx2/IntZhx2/tree/main/smart_agent)

## 需求描述

我们选择旅游规划作为场景。用户可以说出目的地、交通方式、天数和需要到达的时间，助手根据这些条件查询天气、路线或景点，再整理为行程建议。用户还能继续追问、切换历史会话，并要求保存和下载文档。

这个场景需要把对话和操作连起来：模型负责理解需求和选择工具，Python 工具负责请求接口、读取或保存数据。只生成一段攻略文字无法证明工具已经执行，所以界面同时展示工具名称、参数和返回结果。

## 业务流

1. 用户输入旅行需求，也可以使用浏览器语音输入。
2. 服务读取当前会话的历史，把工具说明和对话发给配置的大模型。
3. 模型选择需要的工具，程序验证参数后执行。
4. 天气、路线、景点工具返回数据或明确的错误信息。
5. 模型据此回答；需要更多信息时继续调用工具。
6. 本轮完成后保存对话；用户可继续追问或导出 Markdown。

例如输入「广州两日游，全程地铁，周六 15 点想去广州塔」，助手可以查询城市天气、两地交通和广州塔信息，再给出带缓冲时间的建议。当前天气不能代替周六预报，路线耗时也不能保证未来准点，这些限制会在提示和结果中明确说明。

## 实现说明

项目使用 Python 标准库实现后端，网页采用 HTML、CSS 和 JavaScript。

- SmartAgent 负责模型和工具之间的循环，最多执行 6 轮，再根据已有结果汇总。
- LLMClient 使用 OpenAI 兼容的 Chat Completions 接口，地址、模型名和 Key 由使用者配置。
- MCP 层实现初始化、通知、工具列表和调用等消息子集，并提供独立 stdio 入口；尚未实现完整协议全部能力。
- ConversationMemory 保留当前执行轮的全部工具消息，完成后按完整历史轮次裁剪。
- SessionManager 使用 JSON 文件保存会话，每个会话使用独立上下文和执行锁，写入采用临时文件加原子替换。
- 网页显示工具轨迹、对话历史、语音按钮及导出入口。

部分广州景点有本地静态参考信息，其他数据按接口实际返回处理。查不到或接口失败时，应明确显示缺失，不能把一般经验建议写成实时查询结果。

## 修复和测试

验收时发现，文件名直接拼接可能导致越界写入，共享对话内存可能造成串话，按消息条数裁剪还会丢失正在执行的工具结果。这些问题分别改为工作区内独占创建文件、按会话隔离，以及保留完整当前轮。

我们也补上了请求参数校验、Cookie 与同源检查、模型地址变更后的 Key 处理，以及 Markdown 链接的协议和属性过滤。模型 Key 不进入源码；网页配置文件只保存在本机并限制文件权限。

运行测试：

```bash
python3 smart_agent/main.py --test
node --test smart_agent/tests/test_frontend_security.js
```

Python 测试包含本机 HTTP 服务和本地模拟模型的完整工具循环，前端测试检查安全渲染和状态切换。它们用于验证程序行为，不代表真实服务商、地图 Key 和麦克风已经联调完成。实际验收记录见 docs/acceptance.md；如需填写覆盖率，应另行生成覆盖率报告。

## 当前不足

目前是本机单用户应用；没有数据库，使用本地 JSON 持久化。MCP 只覆盖工具消息子集，没有完成所有客户端互通验证。当前天气、静态景点资料和路线估计均有适用范围，模型生成的时间安排还需要用户核实。

后续可增加指定日期的天气预报、带来源和更新时间的资料，以及程序化的时间冲突检查。
